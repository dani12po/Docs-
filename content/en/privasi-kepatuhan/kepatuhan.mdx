## KYC Model

KORAMP itself is wallet-first with no internal KYC — a wallet address is the customer identity, and KORAMP collects no identity documents. However, since fiat processing is handled by MoonPay as the **merchant of record**, MoonPay performs KYC/AML on users during the payment flow, as required by the applicable regulations in the user's region.

<Callout type="info" title="Compliance responsibility split">
KORAMP does not store KYC data; identity verification, screening, and fiat transaction compliance are handled by MoonPay. KORAMP only stores on-chain transaction traces and order metadata. Trade-off: KORAMP does not run its own identity-based compliance mechanisms (e.g. classic Travel Rule) — that responsibility sits with MoonPay on the fiat side.
</Callout>

## What Is Visible

| Data | Public on-chain | Visible to KORAMP |
|---|---|---|
| User wallet address | Yes | Yes |
| Platform wallet address | Yes | Yes |
| Asset and amount of transfers between KORAMP and the user | Yes | Yes |
| Sender and recipient of the user's other transfers | Yes | Yes |
| User's private balances | Yes (public chain) | Yes (public chain) |

Because KORAMP uses **public** on-chain transfers, sender, receiver, and amount are visible to anyone reading the blockchain. KORAMP does not offer private/encrypted transfers.

## Audit Trail

Every significant event is recorded:
- **AuditLog** — important actions with actor and metadata.
- **LedgerEntry** — double-entry records (CREDIT/DEBIT) per wallet and asset.
- **MoonPayWebhook** — idempotent webhook records keyed on event type, transaction id, and updatedAt.

## Limits and Abuse Prevention

- Progressive IP bans for abuse patterns.
- Redis-backed rate limiting.
- Security events aggregated per hour bucket (deduplicated, bounded).

See [Architecture → Security](/docs/en/arsitektur/keamanan) for details.
